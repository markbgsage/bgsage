# CPU time in truncated rollouts

On the complete 16-thread Linux panel, 1T took **6.118 s** vs 8.417 s at the preceding release, 2T took **45.869 s** vs 61.510 s, and 3T took **185.208 s** vs 219.263 s. All five game plans got faster at all three strengths. Across all seven levels every full checker ranking and all 700 cube decisions agreed. None of the 33,068 comparisons with rollout truth crossed the material threshold in either direction. [All-level comparison and accuracy](results.md) · [Linux full responses](qualified/linux/full_outputs.zip)

A Linux 3T repeat with the selected build running first took 169.234 s vs 197.465 s, a 14.3% reduction. Across both run orders 3T used 14.9% less wall time than the preceding release. Every public response in the repeat matched the corresponding build's first run. [Order-reversed 3T verification](qualified/linux-3t-candidate-first/verification.json)

On Windows the same three panels took **5.900 s** vs 8.740 s, **42.754 s** vs 57.157 s and **169.495 s** vs 207.159 s. Relative to the original Windows engine before any optimization, these are **5.94×, 4.62× and 3.31× faster**. All checker rankings and cube decisions agreed with the preceding engine, with zero material changes against the reference. The compiled regression suite passed all 235 tests. [Windows full responses](qualified/windows/full_outputs.zip) · [Regression results and asset identities](qualified/windows-regressions.json)

With warm default-seed analyzers and checker progress enabled, ten 2T checker calls took 11.682 s at the original revision, 4.182 s at `82e6397` and 2.759 s at the selected revision. The selected scheduler emitted more frequent progress events, so applications that do synchronous work in a callback can see a different wall-time ratio. With two logical CPUs and models on disk-backed Linux storage, the 300-call 1P panel improved 171.83× over the original revision and the 2P panel improved 8.46×. At 1P this saved an average 17.4 ms per cube call. [Default-seed and progress experiment](app-style/README.md) · [Low-ply storage and CPU experiment](inline/README.md)

The 2T profile spent 74% of measured worker time choosing the five probabilities for each of the 21 dice outcomes used in variance reduction. Those rolls share a starting board, a model and a cube state. Evaluating a common neural base and reusing an endpoint reached by different dice removes work inside nearly every simulated turn. At 3T the largest cost was the search at truncation, 36% of worker time. The same pre-roll base also works inside that search. [Phase profile by API](profile/README.md) · [Current rollout algorithm](../../../../ROLLOUT.md)

The timing panel has 300 public calls per strength, covering 100 checker plays, 100 cube actions and 100 post-move evaluations. Each level has 4,724 probability and equity observations with independent full-game references. The release experiments keep the public presets, promotion rules, filter sizes, trial counts, variance reduction and seeds. The benchmark compares every legal checker alternative and saves full responses, including standard errors. ## Ten ideas tested

The smaller panels below isolate individual costs. They use different numbers of positions and workers. The full-corpus timings in the linked results measure the combined release.

| Idea | Measured outcome | Decision |
| --- | --- | --- |
| 1. Compute a single pre-roll neural base for all 21 dice outcomes. Save each winner's probabilities and use its value for the played move when the policies agree. | On ten Linux cube positions, per-roll evaluation took 2.271 s at 2T and 7.476 s at 3T. Sharing the base took 2.135 s and 7.320 s. [Dice comparisons](dice/seconds.json) | Keep |
| 2. Reuse a legal endpoint reached by different dice at the same node. | On a second panel of 30 calls per level across the three APIs, deduplicating the neural evaluations took 9.40 vs 10.20 s at 2T and 36.21 vs 41.00 s at 3T. All fields matched between arms. Collision replacement preserves each roll's original candidates and tie order. [Timing](dedup-repeat/seconds.json) · [Game plans](dedup-repeat/by_plan.json) | Keep |
| 3. Consult the shared VR result before generating all 21 candidate lists. | A hit needs legal boards only for the sampled dice. The cached indices come from canonical dice order. The shared-fan experiments include this change, and the native comparison checks forced passes and probability recovery. Its wall-time effect was measured together with the fan. [Complete trial outputs](dice/calls.jsonl.gz) · [Native check](qualified/fan-check.json) | Keep |
| 4. Reuse a pre-roll neural base in the deeper checker, cube and horizon trees inside a trial. | On the same ten cube positions the change took 2.030 vs 2.135 s at 2T and 6.598 vs 7.320 s at 3T. The subset of legal plays admitted by each filter stays the same. [Variants and patches](dice/source_patches.zip) | Keep |
| 5. Form the three static sibling-batch neural deltas directly from the boards and omit unrequested Python progress reports. | The combined change saved 1.9% at 2T and 1.8% at 3T on 20 public calls. All fields matched. A separate regression exercises progress callbacks and cancellation. [Evaluator study](evaluator/README.md) | Keep |
| 6. Give workers smaller trial assignments during short parallel rollouts. | With 16 workers, one trial per claim saved 19–24% at 1T, 5% at 2T and 4% at 3T on stratified samples. All 390 alternate responses matched the eight-trial controls exactly. Full-game scheduling retains eight trials per claim. [Four assignment sizes](dispatch/README.md) | Keep |
| 7. Allocate the two-million-entry shared search table on its first actual use. | Fresh processes used about 288 MiB less memory across the measured 1T–3T calls and constructed the analyzer around 35 ms faster. A configuration-only allocation gate saved memory at 1T alone. [RSS, cold and warm measurements](scalar_cache/README.md) | Keep first-use allocation |
| 8. Share completed two-ply subtrees between workers. | An additional 3 MiB table hit on 11.0% of probes but saved only 0.8% overall, with slower checker calls. [Cache experiment](dispatch/README.md#shared-two-ply-tree-experiment) | Drop |
| 9. Fuse the sigmoid with the five output sums or retain a larger hidden-layer tile in registers. | On 1,422 legal siblings, median time was 839 ns per candidate with the incumbent kernel, 851 ns fused, and 837 ns with the larger tile. [Kernel distributions](evaluator/kernels.json) | Drop both |
| 10. Replace the native exponential with a shorter polynomial. | The kernel was about 2% faster. The public 2T and 3T samples gave mixed results and the screen overlapped other CPU work. [Kernel and public accuracy](evaluator/README.md#neural-microbenchmarks) | Drop |

A custom checker policy that launches another rollout exposed a separate correctness issue. The parent held an index into a worker's candidates while the child reused the same vector. Each active generator now owns its candidate buffers for the duration of that call. The early-checker example previously returned different cube decisions at one and two workers. Both now give No Double with no-double equity 0.3725155 and double/take equity 0.3370189. [All 18 recorded calls and reproducer](dispatch/nested/README.md)

## Verification and reproduction

The independent move-selection probe uses 2,008 input boards, three driving cube configurations, and every legal roll. On the optimized path all 98,973 winners agreed with the per-roll selector. The largest same-board probability difference was 0.000000656. The probe counted 783 forced passes and 1,311 delegated board/cube combinations. Additional cases cover the exact database, derived strategies, terminal positions and an empty candidate list. [Probe source](check_fan.cpp) · [Board and weight inputs](probe_inputs.py) · [Recorded counts](qualified/fan-check.json)

For the embedded full-game check, each build made 12 public calls with 36 games per rolled alternative, 3P checker and cube policies, variance reduction and 16 Windows workers. The same six benchmark calls ran twice in opposite build orders. Together they took **7.593 s** vs 8.595 s, a **1.13× speedup**. The checker, cube and post-move totals each improved. All rankings and decisions matched, and all 180 observations scored against the frozen references stayed within the material thresholds. [Full-game calls, per-API results and build identities](qualified/fullgame_guard_16.zip) · [Verify and package the run](package_guard.py)

The paired public runs use separate processes for each build and preset and rotate build order by level. Both platforms use 16 logical CPUs, the production Stage 11 weights and the same bearoff database. The timing interval starts after analyzer construction and ends when the public call returns. Each platform has a preceding-release control at `1ecca39`. The historical comparison uses `139427d`. On Linux its parallel truncated measurements include the isolated cache-publication fix needed to obtain a repeatable original result. [Historical build and manifests](historical-linux/replay.py) · [Historical build identity](historical-linux/provenance.json)

Build both CPU extensions for the same Python ABI and put each compiled module and corresponding source tree under the engine checkout. Include the matching Stage 5, 9 and 11 weights under `models/` and the one-sided database under `data/` in the source export used for regression tests. From the engine root, run the following once per platform, using fresh output directories. On Windows the recorded run used `--candidate-first`. The report generator uses the same rollout truth file used by the public benchmark.

```sh
study=data/multi_ply_benchmark/experiments/truncated_pass2
python -B data/multi_ply_benchmark/experiments/search_pass3/paired.py \
  --baseline BASELINE_BINARY_DIR BASELINE_SOURCE --candidate RELEASE_BINARY_DIR RELEASE_SOURCE \
  --run-dir logs/local-truncated-cpu --output build/local-truncated-report --levels 1P 2P 3P 4P 1T 2T 3T
python -B "$study/regressions.py" RELEASE_EXTENSION RELEASE_SOURCE/python build/local-truncated-tests.json
```
